## 测量方法与结果

同一 `LoadJankBenchmarkTest` 在未改动生产 HEAD 和修改后运行；基线执行前 `git diff -- app/src/main` 为零。冷 = 新 repository + 删除 parsed cache 后 load；磁盘暖 = 新 repository 保留 parsed cache；内存暖 = 同 repository 重开。每种至少两次。OS 页缓存不驱逐，因此“冷”不是设备冷启动。首次 window / 图片 ready 包括 load wall time，不包括真实 Compose 绘制与 GPU 上传。所有数字标 **主机测量**。

Find X9 Pro：300ms 占位/首屏、无 >100ms 帧、文字 ≤1.5s、漫画 ≤1s、翻页/滚动 P95 ≤16.7ms、进程峰值 ≤256MB、导入中书架滚动全部 **待真机**。Robolectric 无法验证 120Hz/SurfaceFlinger/GPU 帧时间或 Android 进程峰值。

每格为两轮 **主机测量 ms**。`open` 计 repository.load（冷含完整解析与 JSON 写入，暖含反序列化或内存读取）；`ready` 计 load + 第一个 12,000 UTF-16 窗口 / 2160×4800 上限 CBZ 解码，不含 Compose、GPU 上传、占位最短停留与淡入。文字固定 1000×2200px、density/scaledDensity=3、默认 ReaderSettings，使用系统 Typeface.SERIF（并未加载 App 的思源宋体/BookAssets）；harness 不实例化 ReaderCanvas/Compose 或启动邻窗预取；JDK17，Robolectric SDK35 native graphics。EPUB 13,307,323 UTF-16 字符；TXT 精确 10,485,760 字节，harness 确定性生成到 `/tmp/lyric-load-10m.txt`；CBZ 是 `/workspace/lyric-test-500p.cbz`（500 页/10 章）。先完整导入，再清 parsed cache 冷开、重建 repository 磁盘暖开、同实例暖开，每轮结束移除夹具。新 parser 输出供暖开使用；未单独声称旧格式缓存也有同等收益。EPUB 超出既有 32MiB BookMemoryCache 预算，“同实例暖”依然会反序列化，不冒充内存命中。

单线程 UI 替身的 10ms 探针最大队列等待：修改前 **3ms 主机测量**，修改后 **8ms 主机测量**。包括调度/GC 噪声，不能作为 Android Main 阻塞时长。真实主线程最大任务时间、设备帧分布、GPU 和 Android 进程峰值内存在本机不可测。TXT 磁盘暖开轻微变慢，CBZ 有小幅波动；两轮不足以声称统计显著改善。EPUB 冷 ready 从 2899/2554ms 降到 2100/1744ms，但仍未达到 1500ms 的目标。

## 剩余风险与 Find X9 Pro 复验

- 整书 EPUB/TXT parse 和整本 JSON 仍是 eager；首次重解析仍需等全文与缓存写入。此次保留既有 canonical text/锚点与缓存兼容性，没有引入需要部分 Book / 目录/定位重构的流式 parser。主机 EPUB 冷开仍超目标。
- 原有内存预算不是整个进程的峰值预算：漫画共享位图预算最多 96MiB，BookMemoryCache 最多 32MiB，Coil、BookAssets、正文/JSON/DOM、系统图层和 native 渲染还需叠加。旧大 JSON、legacy 映射和 Decode/GC 可能造成全局暂停；`PageBitmapBudget` 原有 IO 路径的显式 GC 尚在，未假装其无法影响 UI。
- 很长的单章仍会在后台分窗补齐本章页数，显示完整总页数的时间随长度增长；首次字体加载、GPU 纹理上传需真机 trace。旧 `ReaderCanvas.drawSkeleton` 仍用于已进入阅读后的重新排版，初次打开由新外层策略完整遮住。
- 漫画 header 缺失/PDF 原 metadata 没有页面尺寸时，解码前暂用保守比例；已知 CBZ 尺寸按原比例，解码后更新首图/双页比例。错误页保留重试/跳过。需要不同 PDF 纸张、恢复到异形页和超长条漫的视觉复验。
- 生命周期 `pause()` 最多 2s 的同步持久化屏障、KillCheck 开启时同步 SharedPreferences commit 仍为既有风险，未改其耐久/自测契约。导入期间真实书架帧率依然需要设备测试，后台 dispatcher 证据不是滚动帧率证明。

Find X9 Pro 在固定 120Hz、记录系统/温度/电源条件后，各样本清解析缓存和进程冷开，再各做缓存暖开；保留 Perfetto 与 frameTiming 原始分布。检查从书架 tap 起 300ms 内占位或正文、首屏是否包含防闪停留/淡入、加载任何 >100ms 帧、文字 1.5s / 漫画 1s；翻页/条漫/书架导入中滚动 P95 ≤16.7ms；同时测 Android Java+native+graphics 总峰值 ≤256MB。所有这些验收项均 **待真机**，不能从这里的主机表勾选通过。
