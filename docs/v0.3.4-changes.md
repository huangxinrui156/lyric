# Lyric v0.3.4: large EPUB import (剑来)

versionName 0.3.4 / versionCode 7, based on 0.3.3 (2b74889).

## Symptom
Importing 剑来 (18.6 MB EPUB, 1248 XHTML chapters, 13.3M characters, about 41 MB uncompressed) stayed at 「正在导入 0 / 1」 with an empty progress bar.

## Root cause
The import was not deadlocked. It was a heavy single-book parse with no progress feedback inside the book:
1. **CSS matching cost elements × rules × selector parsing.** `Element.is(String)` re-parses the selector string on every call. 剑来 has about 260k elements, and each one was matched against every rule of the two stylesheets (fonts.css + stylesheet.css) in each of the 1248 chapters.
2. **Every chapter was parsed by Jsoup twice.** The second pass only collected `<style>` blocks for @font-face.
3. **The parse cache was built as one huge String.** `json.encodeToString` produced a 48M-character String (about 96 MB on the heap) on top of the 41 MB of uncompressed ZIP entries and the Book itself. The test JVM threw an OutOfMemoryError on this. A phone near its heap limit spends its time in GC thrash and looks hung. Reopening also used `readText()` on the whole file.
4. **No progress inside a single book and no timeout.** The UI showed `done/total` across books only, so 0 / 1 stayed until the book finished.

The 0.3.3 ICU `}` escape is still correct. An audit of all regex literals found no other unescaped `{` or `}`. The remaining braces are either escaped or real `{n}` quantifiers.

## Changes
- `EpubLayout.Rule.evaluator`: each selector is compiled once with `QueryParser.parse`, and matching uses `Evaluator.matches(root, el)`. Rules are cached per stylesheet set, so every chapter reuses them.
- Inline `<style>` text is collected in the main chapter loop, removing the second parse pass. TOC chapter lookup uses a hash map instead of `indexOfFirst`, which was O(toc × chapters).
- The parse cache is streamed with `encodeToStream` and `decodeFromStream`. The manifest sets `largeHeap="true"`.
- `ImportProgress` adds a per-thread hook. The parser calls `tick()` once per chapter, so the shelf shows 「解析章节 x / y」 and the progress bar fills within the book. A 180 s parse deadline throws a `TimeoutException` with the stage and chapter, which appears in the existing error dialog and copy button. Coroutine cancellation is checked on every tick.

## Timings (JVM on the box, Robolectric for the full pipeline)
| | before | after |
|---|---|---|
| 剑来, parser only | 5.75 s | 2.0–2.3 s |
| 剑来, full import (provider URI → copy → parse → cache → Room) | n/a (the old string JSON hit OOM in the test JVM) | 2.8–3.1 s |
| 剑来, reopen after clearing cache (re-parse) | n/a | 2.1–2.5 s |

Expect the phone to be slower than this JVM. With progress shown and a timeout, it can no longer stay at 0 / 1 indefinitely. This has not been measured on the device.

Tests: `ImportProgressTest` and `LargeRealEpubImportTest`/`LargeEpubPerfTest`. The last two are env-gated and run only when `LYRIC_PERF_EPUB=/path/book.epub` is set; the user's book is not committed. The synthetic generator is in `/workspace/perf/gen.py` (outside the repo).
